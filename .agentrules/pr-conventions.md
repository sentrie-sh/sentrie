# Pull Request Title and Description Conventions

When raising pull requests, follow these rules. The body is drafted in `PR_DESCRIPTION_<branch>.md` ([PR description file](pr-description-file.md)).

- **Description scope:** describe only the changes made in this branch. Don't include or summarize work already on the base branch or merged in from other branches. Don't describe code or logic that was added and later removed during the branch's own history, only what is part of the final diff.
- **Title:** must end with an issue reference, and the title as a whole must read as a natural phrase, not just the changes plus a bolted-on issue tag. The issue number is the branch's number prefix (branch `64-replace-pervas...` is issue `64`).
  - Use `Closes #<issue_number>` for a PR that completes the issue, for example `Fix ExecPolicy panic recovery locking and error join Closes #101`.
  - Use `Updates #<issue_number>` for a follow-up PR that adds to or continues work on an issue that should stay open.
- **PRs with no issue:** a change to working conventions or repo tooling (`.agentrules/`, `AGENTS.md`, editor and CI config) does not need an issue invented for it. Such a PR carries no issue reference in its title, states in the body that it is a standalone conventions change, and wires no Development link. Everything that changes the product still takes an issue and follows the rule above.
- **Agent rule PRs:** a PR that changes agent rules (`.agentrules/` or `AGENTS.md`) starts its title with `[AgentRule] `, followed by the usual natural phrase, for example `[AgentRule] Move agent conventions into .agentrules/ and adopt the dryft-os working rules`. The prefix makes rule changes easy to spot in the PR list and in `main`'s squash history.
- **Workflow PRs:** a PR whose purpose is a change to the GitHub Actions workflows under `.github/workflows/` starts its title with `[Workflow] `. This holds even when the PR also updates the rule that documents the workflows ([GitHub Actions](github-actions.md)): the prefix names what the PR is for, not every file it touches, so `[AgentRule]` is kept for PRs whose purpose is the rule itself. One prefix per title. An editor-config-only tooling PR carries no prefix.
- **Link the issue (Closes PRs only):** for a PR that completes an issue, link that issue in the PR's "Development" section so the PR and issue are connected. Do this explicitly (GitHub UI, or `gh api graphql` `addCloseIssueReferences`). The title's `Closes #<issue_number>` keyword alone does **not** reliably populate Development; keep the keyword for close-on-merge behaviour, and still wire Development by hand.
- **Updates PRs must not link Development:** a Development link *is* a closing reference, so merging a PR linked to an issue closes that issue, whatever the title says. A follow-up PR (`Updates #<issue_number>`) therefore references the issue in its title and body only and never wires Development. Watch the body too: GitHub parses closing keywords anywhere in the description, so a sentence like "this would close #196" links and closes #196 on merge. Rephrase it, for example "the issue stays open until #196's last layer lands". `removeCloseIssueReferences` undoes an accidental link.
- **Sections:** Summary, What this PR does, Changes by area (one `###` subheading per area), Review notes, Testing notes, Dependency changes. Add a Design rationale section only when a non-obvious design decision needs justifying. Dependency changes cover what `THIRD_PARTY_POLICY.md` asks for: license, compatibility, motivation, and vendoring status, or "None". When `go.mod` or `go.sum` changes, `deps-policy-check.yml` fails unless that section (`## Dependency changes`, or the older `## Dependencies`) holds more than `- None`.
- **Review notes:** keep them current, covering every critical area reviewers should concentrate on.
- **Style:** keep it concise. Prefer short bulleted points, one main idea per bullet, sub-bullets where helpful, no filler language.
