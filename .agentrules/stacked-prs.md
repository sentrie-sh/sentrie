# Split Large Changes into Stacked PRs

A change too large to review comfortably ships as a stack of small PRs, each testable on its own, merged bottom up into `main`.

**Why:** Large PRs are hard to review and to reason about. A stack keeps each diff to one idea, and every layer carries its own proof.

**How to apply:**

- **When to stack:** plan a stack whenever a task would exceed about 800 changed lines of hand-written code. Generated code (`make gen` output), `lang_test` fixtures and golden files don't count toward that. Split along seams that each leave the tree working, such as a primitive before its caller, a refactor before the feature, or a grammar and parser change before the runtime that evaluates it. The threshold sets where to cut the feature code; each cut carries the tests that prove it. A task that is itself only tests can be one PR.
- **Each layer stands alone:** it passes `make test` (which includes the graph check) and `make lint` on its own ([Build and test](build-and-test.md)), and it adds the tests that prove its own behaviour. Tests ship in the same layer as the code they prove: never split a stack by moving tests into a layer of their own. Code that isn't reachable yet, such as an unregistered builtin or a syntax node the parser doesn't produce yet, is fine when tests exercise it. Each layer updates the graph nodes its own change makes false ([Codebase knowledge graph](codebase-knowledge-graph.md)).
- **Branches and worktrees:** name branches `<issue>-<n>-<slug>`, counting up from the bottom, for example `88-2-typed-lambdas`. Cut the bottom layer from `main`. Give each later layer its own worktree cut from the layer below: `git worktree add -b 88-2-typed-lambdas worktrees/88-2-typed-lambdas 88-1-derive-parser`. Keep one journal file and one PR description file per branch.
- **Settle branch names before the first push:** whenever a task is likely to stack, name the bottom layer `<issue>-1-<slug>` from the start, so a later split needs no rename. Renaming a pushed branch on GitHub (`gh api -X POST repos/sentrie-sh/sentrie/branches/<branch>/rename`) does not move its PRs: it closes every open PR whose head is that branch, and the closed PR cannot be reopened because its head ref is gone. If a pushed layer must still be renamed, open a new PR from the new branch and comment on the old one pointing to it.
- **PR base and titles:** while a layer is open, its PR's base is the branch below it, so the diff shows only that layer. Every layer except the top one uses `Updates #<issue>` and gets no Development link. The top layer uses `Closes #<issue>` and gets the Development link ([PR conventions](pr-conventions.md)).
- **GitHub PR stack:** once every layer is open, the layers are grouped into one native GitHub PR stack. The API has no mutation for grouping, so the owner groups them in the web UI. The agent then checks the stack through GraphQL: `PullRequest.stack` gives the stack's base and size, and `stackEntry.position` should equal each layer's number.
- **Draft until next:** only the bottom open layer is ready for review. Keep every layer above it in draft, so review and CI happen once per layer, when that layer is next to merge against `main` ([GitHub Actions](github-actions.md)).
- **Merging, bottom up into `main`:** for PR3 on PR2 on PR1 on `main`, PR1 merges first. Never merge a layer into the branch below it, and never merge a stack as one combined PR. The repo allows squash merges only and deletes merged branches.
  1. Merge PR1 with the asynchronous merge API, pinned to the head CI passed on: `gh api -X PUT repos/sentrie-sh/sentrie/pulls/<PR1>/merge-async -f merge_method=squash -f sha=<head>`. `gh pr merge` refuses a PR in a stack. The endpoint also merges every open PR below the one named, so name only the bottom layer. It returns `pending` with a UUID; `GET .../pulls/<PR1>/merge-async/<uuid>` reports `merged` and the merge commit.
  2. GitHub restacks the rest. Because merged branches are deleted, GitHub retargets PR2 to `main` and rebases every layer above onto the squash commit, dropping PR1's original commits. Check that PR2's base is `main` and its head's parent is the merge commit. No local rebase or force-push is needed.
  3. Mark PR2 ready for review (`gh pr ready <PR2>`), which starts its CI against `main`. Wait for the run on the current head, then merge PR2 the same way.
  4. Repeat up the stack.
- **When GitHub cannot restack:** if another PR merged into `main` touched the same lines, the next layer shows `CONFLICTING` against `main` and keeps its old commits. Fetch `main` and rebase that layer onto it, naming its old parent: `git rebase --onto origin/main <old-lower-sha> <branch>`. Resolve the conflict, record it in the layer's journal and rerun the layer's checks. Then rebase each layer above onto the new layer below it. GitHub's restacks moved the remote heads after the last fetch, so `--force-with-lease` against the tracking refs fails. Pin each lease to the head GitHub has now: `git push origin --force-with-lease=<branch>:<sha from gh api repos/sentrie-sh/sentrie/branches/<branch>> ...`, all affected branches in one push.
- **Review changes to a lower layer:** rebase every layer above it onto the new tip (`git rebase --onto <lower-branch> <old-lower-sha> <upper-branch>`), then force-push all the affected branches in one push.
- **Origin touches:** each fetch, push and force-push is an origin touch, so batch the layers that are ready into one `git push`, per [Batch origin access](origin-access.md). Retargeting, marking ready and merging go through the GitHub API (`gh`) and prompt for nothing.
