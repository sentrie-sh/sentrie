### 21:13 - Accept keyword segments in declaration and type names
- `parseFQN` now reads every segment after `/` with `advanceNameOrKeyword`, so `namespace constraints/in`, `namespace text/string`, `import decision ok from text/string/p`, `shape T with text/string/Item { ... }` and a named type `text/string/Item` (fact, let, lambda, shape field, and the type after a cast's `as`) all parse. Every one of those positions goes through `parseFQN`, so they agree by construction.
- First segment stays an identifier, with a clearer error (`expected Ident, got keyword 'in': the first segment of a name cannot be a keyword`). Reason: `parseTypeRef` dispatches on the first token, so `string` must keep its type meaning there; allowing a keyword first segment in a namespace declaration would create namespaces whose shapes no type position could name.
- Expression positions stay identifier-only and unchanged: a derive callee `com/ex/f(x)` and the right of `is` are division chains flattened by `ast.FlattenSlashIdentChain`, not FQNs. A keyword after `/` already has a meaning there (`a/not b` is `a / (not b)`, `a/true` and `a/null` divide by a literal), so accepting keywords would change what valid programs mean. Pinned by tests. Consequence: a derive in a keyword-segment namespace cannot be called by slash FQN, and `x is text/string/Item` does not parse; use a type position (`fact`, `let`, cast) or a shape in the caller's namespace.
- Cast target types now accept keyword segments (it is a type position read by `parseFQN`). No valid program changes meaning: after a type name, `/` was always consumed as a path separator and anything but an identifier after it was an error.
- Found and fixed a pre-existing parser panic on the path users of this feature hit first: `constraints/in/f(1)` in a rule crashed `sentrie validate` with a nil pointer in `parseCallExpression`, because the Pratt loop handed a nil left operand to the next infix handler after the `in` operand failed. The loop now returns nil once the left side is nil. Separate commit, with its own test that fails without the guard.
- Index and runtime needed no change: namespaces are keyed by the joined string, and `ResolveSegments` splits CLI and HTTP paths on `/` without looking at keywords. End-to-end runtime test validates and executes a `text/string` namespace whose shape is a base and fact type in `app`, and whose decision `app` imports. Repro packs c2 and c2b validate and execute (`sentrie exec constraints/in/p/ok`, `text/string/p/ok`).
- No formatter exists; `ast.FQN.String()` joins parts with `/`, and the parser test reparses the printed name.
- Grammar (`grammar.peg`, `grammar.ebnf`): `FQN = IDENT ("/" (IDENT / KEYWORD))*`, with a note on the first segment and expression positions.

### 21:26 - Accept keyword segments in expression-position names too
- Review came back CHANGES: the maintainer's decision was "allow keywords", and the issue asks slash-qualified references and derive FQNs to agree with namespace declarations. My earlier reasoning that every keyword after `/` is ambiguous in an expression was wrong: only six keywords have prefix handlers (`not`, `true`, `false`, `unknown`, `null`, `transform`), so for every other keyword `a/<kw>` was always a "no prefix parse function" error, never a valid program.
- `parseInfixExpression`: when the operator is `/` and the next token is a keyword with no prefix handler, it is consumed as an `ast.Identifier`. The set comes from the prefix table through a new `p.isNameOnlyKeyword` in `parser/parser.go`, not a hard-coded list, so a future keyword prefix handler takes that keyword out of name position. The right operand of `/` is parsed at `INDEX` precedence, where nothing can extend an identifier, so taking the identifier directly is the same as recursing. Only `/` does this: `1 + in` is still an error.
- Now `lib/in/double(2)` calls a derive exported from `lib/in`, and `x is lib/in/Item` checks against its shape. Runtime e2e test validates and executes both, and the CLI was checked by hand (`sentrie validate`, then `sentrie exec app/q/ok` true and false cases).
- Remaining limitation, only: one of the six prefix keywords as a later segment of a name used in an expression. `a/not b` stays `a / (not b)`, `a/true` and `a/null` divide by a literal, `a/true/f(1)` is a call on a division chain, not an FQN. Such a namespace can still be declared, imported from and used as a type.
- Moved the tests that pinned a rejection or the panic from `a/in/...` to the prefix keyword `not` (`a/not/f(1)`): in `TestParseExpressionStopsAfterAFailedOperand`, `TestParseExpressionOperandFailureShapes` and the CLI no-panic test. The expression-position test is now `TestParseSlashChainInExpressionKeywordSegments`.
- `parseExpression`: one nil guard for both paths, `leftExp != nil` in the loop condition and `return nil` before the preceding-comment wrap, so a failed prefix after a comment (`-- note` then `not )`) returns nil instead of a comment node around nil. Checked each half: removing the loop condition makes the `a/not/...` cases panic; removing the final check makes the comment case return a non-nil node. The pipeline.go nil check stays as a defensive check.
- Corrected the rationale in `parser/fqn.go`, `grammar.peg`, `grammar.ebnf` and the `parser.fqn`, `parser.infix`, `parser.parser`, `parser.expression` and `grammar` graph nodes.
