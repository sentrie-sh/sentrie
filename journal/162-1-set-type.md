### 2026-10-31 14:44 - Implement set[T] and the set builtins
- Representation: a set is a `ValueList` with a set tag in the unused `u64` slot (`box/set.go`), not a new `ValueKind`. Elements are distinct and held in one canonical order. Reason: every list-reading path (`in`, `contains`, `count`, indexing, iteration, `MarshalJSON`, the JS boundary) reads a set unchanged and serialises it as a sorted array with no new switch arms; the decision envelope already set the precedent of tagging a container in `u64`. Cost: the tag is lost when a list is rebuilt (`map`, `filter`, module return), and a set equals a list holding the same elements in the same order.
- Elements: null, bool, number (not NaN), string, and lists/dicts of those. The canonical order (kind rank, then value; lists element-wise, dicts entry-wise in key order) returns 0 exactly when `EqualValues` holds, so membership and duplicates are well defined; `-0` and `0` are one element. Undefined, unknown, NaN, documents and callables are rejected with `a set cannot hold ...`. A decision envelope element is stored as its plain dict, since `EqualValues` would otherwise equate it with a bool by state.
- Typeref: `set[T]` parses where `set` is an identifier followed by `[`. `set` is not a keyword, so `set(...)` stays a builtin call and a bare `set` is still a shape name. `x is set[T]` is recognised the same way. `SetTypeRef` takes the list constraint table (`@not_empty()`), so no `make gen` was needed. Additive to the typeref grammar, for #165.
- Builtins (`builtins/set.go`): `set`, `union`, `intersection`, `difference`, `is_subset`, `is_superset`. Decision: each operand of the operations may be a set or a plain list (converted with dedupe), so `is_subset(required, user.scopes)` works directly on JSON facts; the result is always a set. All are strict on undefined/null, like `merge` and `distinct`. Validate-time arity/kind checks come from the `Sig` (kind `list`).
- Fact boundary decision: a JSON array bound to a `set[T]` fact is validated, never deduplicated: a duplicate is an error (`duplicate set element ...`), matching the issue's "validates uniqueness". `set()` and `as set[T]` are explicit conversions and do dedupe. A valid list bound to a top-level (or nullable) `set[T]` fact, let, derive parameter/return or lambda return becomes a set through one `bindTypedValue` step that also covers the #136 truth-value binding.
- Limitation recorded: a `set[T]` nested inside a list, dict, record or shape field is validated (typed, distinct) but stays a list, so it keeps input order in output. The builtins accept lists, so set operations on such fields still work. `[1, 2] is set[number]` is true for the same reason.
- `ContainsValue` binary-searches a set for a scalar needle; other needles fall back to the linear `EqualValues` scan.
- Graph: new nodes `box.set` and `runtime.typeref_set`; updated `box.value`, `builtins`, `ast.typeref`, `parser.typeref`, `parser.is`, `runtime.typeref`, `runtime.typeref_trinary`, `runtime.eval_cast`, `index.builtin_kind`. `make docs-graph` passes.
- Tests: box (order, dedupe, rejection, order agrees with `EqualValues`, binary search agrees with linear scan, operations, tag not surviving a rebuild), builtins (results and exact errors), parser (`set[T]`, nested, bare `set`, `is set[T]`, `set(...)` call), runtime end to end (fact conversion and sorted output, builtins, `in`/`contains`/`count`, `is`, cast, typed let, duplicate and wrong-element facts). box, builtins, ast, parser, index, runtime, constraints and lang_test pass. `make lint` could not run: the local golangci-lint binary panics because it was built with go1.26 against a go1.27 file; not related to this change.
