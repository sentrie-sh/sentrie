### 2026-10-31 14:43 - Resolve calls through let-bound callables
- Runtime: `getTarget` (runtime/eval_call.go) now resolves an identifier callee through a value binding before derives and builtins. `calleeIsBinding` mirrors evalIdent's lookups (locals, lets, and outside a derive body facts and rules); `bindingCallTarget` evaluates the binding like a reference and invokes the callable, or reports `cannot call "v": it is a number value, not a function`. Arity errors come from the existing `padAndValidateCallableArgs`.
- Precedence decision: lexical, innermost first: value binding > derive > builtin > `alias.fn`. Why: it is what the static checker (`isBuiltinCall`, its tests `TestBuiltinCheckBuiltinShadowedByLetAccept` and `TestBuiltinCheckPolicySitesRespectShadowing`) already assumed, it matches identifier resolution in evalIdent, and a builtin added later can never take over an existing user lambda of the same name. The rejected alternative (derive > builtin > let) is backward compatible for `let first = first(...)` but lets a new builtin silently hijack user code.
- Facts and rules count as bindings (as in evalIdent) because evalIdent caches a referenced rule's value as a local, so excluding rules would make call resolution depend on evaluation order. A fact or rule can never be called usefully, so this only turns a collision into a clear error, which validate reports.
- Memoized calls through a binding are refused (runtime and validate): the memo key is the call site plus arguments, so a lambda that captures facts or parameters would be answered from another execution.
- Derive bodies: runtime allows a bound `deriveCallable` or a `lambdaCallable` whose capture has `evalDerive` set (created while evaluating a derive body), and refuses a lambda created outside any derive (it captures facts and modules). Static (`checkDeriveCall`) is a sound subset: only a let bound directly to a lambda literal may be called; calling a parameter or another let is refused. The purity scope now records how each name was bound (`deriveBinding`).
- Unknown callee: runtime says `unknown function "x": ...`; the import error is kept only when the policy imports the name with `use`, with a hint to call it through its alias. New `checkCallTargets` (index/call_check.go) makes validate reject unknown callees, rule calls, non-callable values of known kind, memoized binding calls and let-lambda arity mismatches, as `xerr.CallTargetError` with a span. Validate did not reject unknown callees before (contrary to the brief's "still rejects").
- Unified the two static precedence rules: `runtimeBuiltinCallee` is gone and the shared builtin walk uses `isBuiltinCall`, so nondeterminism warnings and capability checks follow the new precedence. Facts and lets now also win over a policy derive of the same name in the static scope, and parameters over a `DefineShort` derive, as at runtime.
- Fallout fixed: fixture 0017 called an undefined `toUpper` (now a let lambda); fixture 0047's `let first = first(...)` would now call itself (renamed); the capabilities and nondeterminism tests no longer expect the shadowed calls; a runtime test derive `blank` collided with the harness fact `blank` (renamed).

### 2026-11-01 02:34 - Bound lambda recursion with a call depth limit
- Bug from the test agent: `let loop = (n) => { yield loop(n + 1) }` validated, then ExecRule died with a fatal Go stack overflow (unrecoverable, takes `serve` down).
- Fix: `ExecutionContext.callDepth`, copied by both child constructors. `enterCall` (runtime/exec_ctx.go) gives an invocation the call site's depth plus one and fails past `MaxCallDepth` (1000) with `lambda call depth exceeded (limit 1000)` or `derive call depth exceeded (limit 1000)`, wrapping `ErrCallDepthExceeded`. `lambdaCallable.Invoke` and `invokeDerive` apply it. The depth follows the call chain, not the lambda's capture. No global state, so concurrent rules are independent.
- Limit choice: measured with a sandbox program: a 990-level self-recursive let lambda fits in 8 MB of Go stack (4 MB is too little), with and without -race. 1000 levels is therefore over 100x under Go's 1 GB default, and deep enough for real recursion with a base case (a 999-level recursion is tested).
- `evalCall` passes an `ErrCallDepthExceeded` error through unwrapped. Before this, the message carried 1000 nested "failed to call function" prefixes (about 30 KB).
- Static detection: not added. Mutual recursion between let names is already rejected by the existing reference cycle check (`detectReferenceCycle`, a scope-unaware dag). That dag drops self-loops on purpose, so treating a self-edge as a cycle would falsely flag a parameter shadowing its let (`let x = collect(xs, (x) => ...)`). Self-application (`self(self)`) names no let, so no static check can be complete. The runtime guard is the fix.
- Found while testing: my new static call check rejected a block let lambda calling itself or a later let as an "unknown function", because the shared walk bound block lets one at a time. The runtime (`evalBlock`) injects all block lets up front, so `walkScopedExprs` now binds them all before walking the initializers, and refines kinds afterwards. Policy-level and block-level self-recursion now validate the same way, and both stop at the depth limit at runtime.
- Proved the tests bite. With the guard disabled, the recursion test crashes the test binary (`fatal error: stack overflow`), and the derive and call-site depth tests fail. With block pre-binding reverted, `TestCallCheckBlockLetsSeeEachOther` and the block self-call runtime test fail with `unknown function`.

### 2026-11-01 02:50 - Review round 1: bound the stack, allow recursive let lambdas, carry depth into imports
- W1: the 1000-call limit did not bound the Go stack. A body with 400 nested terms per level still overflowed, because stack per level grows with how deeply the recursive call sits in the body. Added a per-evaluation `evalDepthCounter` that every `eval` frame enters and leaves, capped at `MaxEvalDepth` (50000) with `ErrEvalDepthExceeded`. It is shared through the context tree, taken from the call site on lambda invocation, and atomic only to be safe against an escaped callable. Measured: a runaway recursion stopped at 50000 frames used under 128 MB of Go stack (64 MB was not enough), with and without -race, at 400 and 2000 nested terms. The earlier "990 levels in 8 MB" comment held only for trivial bodies and is replaced. Overhead is about 2% on BenchmarkCollectionLambdaRule (10.72 ms to 10.97 ms per op).
- W2: `detectReferenceCycle` walked lambda bodies, so recursive let lambdas (`fac` with a body let, `isEven`/`isOdd`) were rejected as infinite recursion, and a body let aliased a rule of the same name. `addNodes` no longer descends into lambda bodies, since a body is not evaluated when its let is. This supersedes my earlier note that mutual let recursion is rejected statically: it now validates, runs when it ends, and stops at the call depth limit when it does not. Cycles through let values are still rejected.
- S1: an imported decision's nested ExecRule started at depth 0. `ExecRule` now delegates to `execRuleFrom(..., caller)`, and `ImportDecision` passes its context, so the new root context inherits callDepth and the eval counter (`inheritDepth`).
- Tests: `TestHeavyRecursiveLambdaBodyStopsAtEvalDepthLimit` (the reviewer's repro), `TestRecursiveLetLambdas` (replaces the validate-rejection test), `TestImportedDecisionInheritsDepthBudget` and `TestReferenceCycleCheckSkipsLambdaBodies`. Each fails without its fix: the eval limit disabled gives a fatal stack overflow; the lambda-body skip reverted gives "infinite recursion: fac -> v -> fac"; `inheritDepth` removed makes the import test fail.
- `go test ./runtime/... ./index/... ./lang_test/...` passes, the race run of the new tests passes, lint reports 0 issues, and docs-graph passes.
