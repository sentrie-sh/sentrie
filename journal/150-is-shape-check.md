### 15:59 - Tell a type mismatch from a failed type check
- `x is T` must return false for a value that does not conform and still fail loudly when the check itself cannot be made. `validateValueAgainstTypeRef` returned plain errors for both, so the two had to be told apart.
- Added `typeRefFailure` in `runtime/err_typedef.go`, a wrapper that keeps the message unchanged and carries a `mismatch` flag. Mismatch sites: every kind check, the shape required-field and undefined-field checks, the record length check, and `ErrConstraintFailed`. Constraint-argument evaluation errors are wrapped as non-mismatch failures (`errCheckFailed`).
- `isTypeMismatch` lets the outermost marker in the chain decide. That makes a nested field or list item mismatch a mismatch of the whole value (the wrapping `fmt.Errorf("field ...: %w")` keeps the inner marker reachable), and keeps a mismatch raised while evaluating a constraint argument (for example a typed let that fails its type) from turning into `false`.
- Unmarked errors (unknown shape or constraint, unexported shape, namespace not found) are not mismatches, so a future error site defaults to failing loudly rather than to a silent `false`. Ruled out the reverse (marking only the infrastructure errors), whose failure mode is the silent one.
- A constraint checker's own error counts as a mismatch, as `ErrConstraintFailed` already reported it; a checker that fails for a reason unrelated to the value would read as `false`.

### 15:59 - Evaluate `x is T` as a shape and type check
- New `ast.IsExpression{Left, Right, Type}`, modelled on `CastExpression`. The parser (`parser/is.go`) builds it when the right-hand side is type syntax: a type keyword (`string`, `number`, `boolean`, `trinary`, `document`, `list`, `dict`, `record`) parses a full typeref with nullable `?` and constraints; a bare or slash-qualified name followed by `?` or `@` is a shape typeref. Every other right-hand side still builds the legacy `InfixExpression "is"` (equality), so nothing that parsed before changes shape in the AST.
- A bare or slash-qualified name with no suffix is ambiguous in the parser (shape or value). The parser sets both `Right` (the name as an expression) and `Type` (the name as a `ShapeTypeRef`), and the index settles it in `index/is_resolve.go`, which runs first in `validate()` so cycle detection, derive purity and the builtin checks never read a shape name as a value. It reuses the scope-aware walk of `forEachBuiltinCall`, generalised to `forEachScopedExpr`/`walkScopedExprs` (the builtin walk is now a filter over it), so block lets and lambda parameters are known at each site.
- Resolution rule: a name that is a shape visible from the site and not a value in scope is a type check; a single name that is both a shape and a value in scope is an index error (either reading would silently flip meaning when a declaration is added or removed, and before this change such code meant equality, so an error is the only non-silent option); a name that is not a shape is the legacy equality, provided every identifier in it is a value in scope, otherwise an index error naming it ("neither a shape nor a value in scope"), which is what a misspelt shape name produces. A qualified name whose namespace exists but lacks or does not export the shape is an error. Ruled out "shape wins" (silent change for existing `x is someLet` code when a same-named shape exists) and "value wins" (a typo'd or later-added let flips a type check to equality).
- Shape visibility mirrors runtime `validateAgainstShapeTypeRef`: policy shapes, then namespace shapes, by the full name; three or more segments look up the exported shape of the prefix namespace. New `(*Index).LookupShape` encodes that and is also used by the runtime when it meets an unresolved node (an index that was never validated).
- Values in scope mirror runtime `evalIdent`: locals, facts, lets, visible derives (the `kindCheckCtx` scope) and, outside a derive body, the policy's rules. In a derive, facts and rules are not in scope, so a fact name on the right of `is` there reports the `is` error rather than the purity check's fact message.
- Runtime `evalIsType`: undefined operand gives false; otherwise `validateValueAgainstTypeRef` against the operand, false on `isTypeMismatch`, any other error propagated; true otherwise. Results are `box.Bool`. A node resolved to a value delegates to `evalInfix` with operator `is`, so the legacy equality is unchanged (including undefined propagation). Under `evalDerive` the check is allowed: it resolves no callee or identifier itself, and the operand and constraint arguments go through `eval`, which applies the derive gates.
- `is not T` is the existing desugaring to `not (x is T)`, which is a definite boolean.
- Ternary clash: `?` after a type is ambiguous with the ternary operator (`x is string ? a : b`). Split `parseTypeRef` into `parseBaseTypeRef` and `parseTypeRefSuffixes`; with `ternaryAware` set, a `?` followed by a token that can start an expression (`canStartExpression`, a registered prefix handler) is left for the ternary. `x as string ? a : b` keeps its old behaviour.
- Constraint arguments in an `is` type are not walked by the derive purity or builtin walks, matching `CastExpression`; noted as a gap.
- Fixture `0019-rule-import-with-with.sentrie` used `user is subject` with no `subject` declared anywhere, which the new check rejects; declared the four names it uses as optional facts. Added `0049-is-type-check.sentrie` and minimal runtime tests (`runtime/eval_is_type_test.go`); the regression suite is another agent's task.
- Found while testing: `validateAgainstDictTypeRef` checks only that the value is a dict and never checks values against the element type, so `{"k": "s"} is dict[number]` is true (and a `dict[number]` fact accepts strings). Left as is: it changes fact and let validation too, so it belongs in its own issue.
